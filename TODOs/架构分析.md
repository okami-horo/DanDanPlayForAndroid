# DDPlayTV 架构评估报告

---

## 一、项目概览

| 维度 | 现状 |
|------|------|
| 模块总数 | 21（1 app + 5 feature + 1 bilibili infra + 7 core + 1 data + 6 repo AAR） |
| 主要语言 | Kotlin 1.9.25，JVM target 1.8 |

| 生产源码 | 约 986 个 .kt 文件 |
| 单元测试 | 80 个 JVM 测试 + 17 个 Instrumentation 测试 |

## 二、结构评估

### 2.1 模块依赖关系图（实际 Gradle 依赖）

```
─────────────────── data_component（纯数据类/实体/枚举）────────────────────
                               ▲
          core_contract_component（路由表/接口契约/StorageFile 接口）
                               ▲
         core_log ←── core_system ──→ core_network / core_database
                               ▲
                      bilibili_component
                               ▲
                    core_storage_component──→ [seven_zip, thunder]
                               ▲
         core_ui_component ────┘
                               ▲
  ┌────────────────────────────────────────────────┐
  │ anime  local  user  storage  player  app       │
  └────────────────────────────────────────────────┘
```

- **依赖方向单一**：经验证，feature 模块之间无直接 import，跨模块导航通过 `ARouter + RouteTable` 完成，符合低耦合目标。
- **`api` 已收敛**：绝大多数 `project(...)` 使用 `implementation`，仅 `core_contract_component -> data_component` 使用 `api`（类型对外暴露有充分理由）。
- **core_storage_component 依赖 bilibili_component**：从分层视角看，一个 `core_*` 基础层依赖了 infra 集成层，是当前最显著的分层偏差（已在治理文档中标注 P1/P2 级问题）。

### 2.2 包命名与模块边界

存在历史性"命名漂移"问题：**多个不同的 Gradle module 共享同一顶层包名 `com.xyoye.common_component.*`**：

| Gradle 模块 | 实际包路径 |
|---|---|
| bilibili_component | `com.xyoye.common_component.bilibili.*` |
| core_storage_component | `com.xyoye.common_component.storage.*`、`com.xyoye.common_component.network.repository.*` |
| core_system_component | `com.xyoye.common_component.config.*`、`com.xyoye.common_component.utils.*` |
| core_ui_component | `com.xyoye.common_component.base.*`、`com.xyoye.common_component.adapter.*` |

这意味着 Gradle 模块边界与 Java 包边界脱节，新成员难以从包名判断代码归属，IDE Navigation 也无法直接反映模块归属。

## 三、设计优点

### ✅ 1. 单向依赖无环，feature 间完全解耦
5 个 feature 模块之间零直接依赖，所有跨模块导航通过 ARouter 路由字符串完成，`RouteTable` 统一定义于 core_contract_component，做到了"合同先行"。

### ✅ 2. 架构文档与代码同步维护
architecture 下有：依赖快照（自动生成）、治理规范（含 DR 决策记录）、日志与 TLS 策略，且配有 `verifyModuleDependencies` Gradle 任务和 CI 门禁，具备主动防止依赖劣化的基础设施。

### ✅ 3. bilibili_component 作为可复用基础设施模块
Bilibili 的签名（WBI/Ticket）、鉴权、CDN 策略、心跳、直播弹幕 socket、MPD 生成等都内聚在同一模块内，且配有单元测试（`BilibiliAppSignerTest`、`BilibiliHeartbeatPolicyTest`、`BilibiliMpdGeneratorTest` 等），可独立演进和测试。

### ✅ 4. player_component 内核抽象层设计
玩家内核通过 `AbstractVideoPlayer`/`InterVideoPlayer` 抽象，分别提供 Media3/mpv/VLC 三种实现，外部依赖统一的 `InterVideoController` 接口，具备替换能力。

### ✅ 5. app 壳层已收敛
`:app` 不再直接依赖 core_network_component/core_database_component，跨域初始化通过 `UserSessionService`/`ManualMigrationInitializer` 等契约服务完成，符合组合根职责边界。

### ✅ 6. 测试覆盖关键基础设施
core_log_component、bilibili_component、core_network_component、core_storage_component、player_component 内核均有较系统的单元测试。

## 四、潜在风险

### ⚠️ 风险 1：`BilibiliRepositoryCore` 是典型 God Class
> **文件**：`bilibili_component/.../bilibili/repository/BilibiliRepositoryCore.kt`  
> **规模**：1774 行、69 个方法

单个类承担了 B 站所有 API 的调用：登录、签名、搜索、播放地址解析、弹幕、历史、心跳、风控……违反单一职责。修改任一功能都需要理解整个文件，且该类的变更极易引入回归。

### ⚠️ 风险 2：`PlayerActivity` 是巨型 Activity
> **文件**：`player_component/.../ui/activities/player/PlayerActivity.kt`  
> **规模**：1290 行、51 个方法

播放器 Activity 承担了视频控制器绑定、弹幕配置、字幕配置、输入事件路由、悬浮窗权限、播放会话生命周期管理等大量工作。即便有 `PlayerViewModel`（269 行）和 `PlayerDanmuViewModel` 辅助分担，Activity 本身依然过重，单测难以覆盖其内部逻辑。

### ⚠️ 风险 3：core_storage_component 职责边界过宽
该模块同时包含：
- 多协议存储实现（FTP/SMB/Alist/BaiduPan/Cloud115/Bilibili/Torrent 等）
- 网络 Repository（`AlistRepository`、`BaiduPanRepository`、`MagnetRepository`、`ResourceRepository` 等 8 个 Repo）
- 媒体代理服务器（`HttpPlayServer`、`FtpPlayServer`、`SmbPlayServer`）
- 视频源工厂（`StorageVideoSourceFactory`、`VideoSourceManager`）
- UseCase（`BilibiliDanmuUseCase`、`VideoScanRefreshUseCase`）
- 文件解析（`MediaResolver`、`PlaybackProfileResolver`）

128 个文件、多个不同抽象层次的类堆积在同一模块，导致单元测试无从入手、依赖注入无法精确控制。

### ⚠️ 风险 4：Repository 使用静态单例模式
```kotlin
// ViewModel 直接调用静态单例 Repository
val result = AnimeRepository.getAnimeDetail(animeId)
```
全部 31 个 Repository 均为对象（`object`）或静态单例，ViewModel 直接持有 Repository 静态引用，导致：
- ViewModel 无法被 mock，单元测试只能依赖 Robolectric 或集成测试
- Repository 的初始化状态全局共享，难以并发测试和隔离

### ⚠️ 风险 5：core_system_component 职责漂移
该模块（64 文件）混合了：应用生命周期（`BaseApplication`）、权限管理（`PermissionManager`）、通知（`Notifications`）、全局配置表（`AppConfigTable`/`PlayerConfigTable`/`DanmuConfigTable` 等 8 个 ConfigTable）、用户 Session（`UserSessionManager`）、密钥存储（`BilibiliTvCredentialStore`/`CredentialCrypto`/`KeystoreAesGcmCrypto`）、工具类（77 个 `utils/*` 文件）。这个"what doesn't fit anywhere else goes here"的模式会持续膨胀。

### ⚠️ 风险 6：包名与模块边界脱节（已在 §2.2 说明）
`com.xyoye.common_component.*` 跨越 5 个 Gradle 模块，对 IDE 跳转、搜索、重构、新成员理解成本均有负面影响。

### ⚠️ 风险 7：无 UseCase 层，调用链核心路径：ViewModel → Repository → Service
当前架构是 `ViewModel → Repository（静态）→ Service/API`，没有 UseCase 中间层。对简单页面合理，但对播放、存储、Bilibili 这类多 Repository 协作、多步骤业务逻辑的场景，复杂编排逻辑散落在 ViewModel 中（`PlayerViewModel` 269 行），难以复用和测试。

## 五、改进建议

### 🔧 建议 1：拆分 `BilibiliRepositoryCore`（高优先级）
按业务域拆为多个聚焦 Repository：`BilibiliAuthRepository`（已存在）、`BilibiliMediaRepository`（播放地址/详情）、`BilibiliDanmakuRepository`（已存在）、`BilibiliHistoryRepository`（已存在）等。`BilibiliRepositoryCore` 降级为内部实现细节，不再对外暴露。

### 🔧 建议 2：core_storage_component 按职责二次划分
可考虑逻辑分区（不必立刻拆成独立 Gradle 模块）：
```
core_storage_component/
  storage/        ← 存储协议实现（现已有 AbstractStorage 等）
  source/         ← VideoSource 工厂与管理
  proxy/          ← HttpPlayServer/FtpPlayServer 媒体代理
  credential/     ← 凭据管理（现已有 credential/ 子包）
```
同时，将 core_storage_component 对 bilibili_component 的依赖隔离到 `BilibiliStorageFile`/`BilibiliStorage` 这两个实现类中，而非整个模块都传递依赖。

### 🔧 建议 3：Repository 由静态单例改为可注入实例
使用构造函数注入（或 Hilt/Koin 等 DI），使 ViewModel 可在测试中替换 Repository 的 Fake 实现，大幅提升 ViewModel 单元测试覆盖率。

### 🔧 建议 4：为复杂业务引入 UseCase 层（渐进式）
不需要全面引入，仅针对多步骤流程（如"启动播放 → 解析播放地址 → 初始化弹幕源 → 建立心跳"）提取 UseCase，减少 ViewModel 的隐式状态机复杂度。参考 core_storage_component 中已有的 `BilibiliDanmuUseCase`/`VideoScanRefreshUseCase` 作为模板。

### 🔧 建议 5：迁移包名，使 Gradle 模块边界与 Java 包一一对应
以迁移 bilibili_component 为例：将 `com.xyoye.common_component.bilibili.*` 改为 `com.xyoye.bilibili_component.*`，配合 IDE "Rename Package" + 全局替换，可分批进行，消除包名混乱。

### 🔧 建议 6：core_system_component 提取 `core_config_component` 或收紧 ConfigTable 放置规则
将 `AppConfigTable`、`PlayerConfigTable`、`DanmuConfigTable` 等从 `core_system` 提取到 data_component 或新的 `core_config_component`（仅含配置键/默认值/读写逻辑），避免 `core_system` 继续扩张。

### 🔧 建议 7：增强 ViewModel 和 feature 模块的测试覆盖
当前 local_component、storage_component（UI 层）、user_component 的单元测试仅有 1-2 个文件，建议补充 ViewModel 逻辑测试（借助 Fakes 替换 Repository），并为复杂 Activity（`PlayerActivity`、`StorageFileActivity`）提取可测逻辑到 ViewModel 或 Helper 类。
