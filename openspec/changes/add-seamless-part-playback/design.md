## Context

当前播放器已经支持“自动播放下一项”，但实现路径仍是完成后再切源：

1. `DanDanVideoPlayer.onCompletion()` 将状态置为完成。
2. `VideoController` 在 `STATE_COMPLETED` 下根据 `isAutoPlayNext` 与 `hasNextSource()` 触发切换。
3. `PlayerActivity.switchVideoSource()` 通过 `indexSource()` 异步解析下一项。
4. `applyPlaySource()` 会执行 `recordPlayInfo()`、`pause()`、`release()`、控制器重置、重新设置播放源并重新启动播放器。

这条链路的优点是逻辑简单、各文件状态天然独立，但缺点也很明显：播放器实例、渲染视图和附加状态都会被整段重建，因此“自动下一项”一定存在可感知停顿。

首版约束已经确认：

- 仅对 `Media3/ExoPlayer` 提供“尽量无感切换”的新路径。
- 下一项直接复用现有顺序定义，不新建“Part/分集识别”语义。
- 不修改现有设置文案与入口。
- 每个视频仍然是独立播放源，不做跨文件外挂资源继承。
- TV 端交互不能退化，不能因为自动续播引入新的焦点或返回路径问题。

## Goals / Non-Goals

**Goals:**

- 在 `Media3/ExoPlayer` 路径下，为现有顺序中的下一项提供低感知停顿的连续续播能力。
- 保持用户停留在当前播放页内完成续播，不要求额外确认或回到列表页重新进入。
- 继续使用现有 `GroupSource` / `indexSource()` 暴露的顺序，不引入新的排序或识别规则。
- 抽出后端无关的顺序续播协调边界，使后续 `VLC/mpv` 接入时能够复用同一套续播 contract。
- 明确“全局播放器偏好持续生效、文件级播放状态各自独立”的边界。
- 在下一项预准备失败时平滑降级，不影响现有“自动播放下一项”能力的可用性。

**Non-Goals:**

- 本次不为 `VLC` 与 `mpv` 引入同等的无感续播能力。
- 本次不新增“Part/分集/相似文件名”识别器，也不改写现有目录或播放列表排序规则。
- 本次不修改现有设置项文案，不新增独立的“无缝播放”开关。
- 本次不实现跨文件字幕、弹幕、外挂音轨的强制继承。
- 本次不重构为全局播放列表管理器，也不要求所有播放源立即升级为多项队列模型。

## Decisions

### 1. 先抽出后端无关的顺序续播协调层，再让 Media3 作为首个适配器落地

顺序续播不应该直接分散在 `PlayerActivity`、`DanDanVideoPlayer` 与具体后端实现之间，而应先抽出统一协调层。建议在 `player_component` 内引入类似 `SequentialPlaybackCoordinator` 的协调对象，并配套一个后端适配接口，例如：

- `SequentialPlaybackCoordinator`
  - 负责续播会话生命周期、下一项预解析、过期回调拦截、降级策略选择。
- `SequentialPlaybackBackendAdapter`
  - 负责把“当前项 + 下一项”的协调结果映射到具体播放器后端能力。
- `SequentialPlaybackStateApplier`
  - 负责在目标项真正生效后，同步标题、播放历史、外挂资源与会话元数据。
- `SequentialPlaybackFallbackSwitcher`
  - 负责在无感续播不可用时回退到现有 `switchVideoSource() -> applyPlaySource()` 重建链路。

首版只提供 `Media3SequentialPlaybackAdapter` 实现；`VLC/mpv` 先挂接 no-op 或 fallback adapter，继续保留现状行为。这样后续其他后端跟进时，新增的是 adapter 能力，而不是重新拆分 Activity 与播放器内核之间的职责。

备选方案：

- 维持当前 Activity/Controller/Backend 直接协作：首版能做出来，但后续后端扩展只能复制编排逻辑。
- 把所有顺序逻辑都塞进具体后端实现：会让业务源模型、状态同步、UI 更新与内核能力耦合过深。

### 2. 仅在 Media3 路径引入无感续播，其他内核保留现状

`Media3/ExoPlayer` 原生具备队列、媒体项切换与预准备能力，是当前唯一适合承载“尽量无感切换”目标的内核。`VLC` 与 `mpv` 现有接入仍以单一数据源为中心，如果一并纳入本次设计，会把范围从“增强现有自动下一项”扩大为“统一三套内核的队列播放模型”，复杂度明显超出首版目标。

备选方案：

- 同时为三套内核扩展队列能力：范围过大，验证面过宽。
- 只优化现有 `switchVideoSource()` 而不使用 Media3 队列：仍然需要 `release/recreate`，无法达到目标体验。

### 3. 继续使用现有顺序定义，下一项解析仍由源层负责

下一项仍然由当前 `BaseVideoSource` 的顺序关系决定，具体通过 `getGroupIndex()` / `indexSource(index + 1)` 获取。这样可以让同目录视频、播放列表、Bilibili 多 P 等现有顺序语义全部自动受益，而不需要在播放器侧额外理解“Part”。

备选方案：

- 通过文件名、正则或相似度推断下一项：会引入误判，并与当前已有排序逻辑冲突。
- 为本次能力新增独立播放列表模型：会和现有 `GroupSource` 语义重叠，收益不成比例。

### 4. 续播会话必须携带稳定的身份令牌与媒体项标识

当前设计不能只描述“预解析下一项”和“切换后更新当前源”，还必须定义稳定的身份模型，否则手动切源、错误恢复、后台恢复或重复预准备都可能把过期结果同步到错误目标。

建议协调层持有统一的 `SequentialPlaybackSessionToken`，至少包含：

- 单调递增的 `generation`
- 当前逻辑源的唯一标识
- 当前会话绑定的后端类型

同时，为每个进入后端队列的媒体项分配稳定的 `queueItemId`。所有异步预解析结果、后端媒体项切换事件和状态同步请求都必须携带 `sessionToken + queueItemId`。协调层仅在以下条件同时满足时才应用回调：

- `sessionToken` 仍然是当前活动会话
- `queueItemId` 与当前期望切换目标匹配
- 当前播放器后端与会话绑定一致

任何手动切源、播放器释放、错误恢复、后台恢复导致的重建，都必须使旧 `sessionToken` 失效。这样后续无论哪个后端实现该能力，都只需要遵守同一套 token 校验与失效语义。

备选方案：

- 只靠 source uniqueKey 判断回调是否过期：无法区分同一 source 上的多次准备与恢复过程。
- 完全依赖 Media3 的 mediaId：对后续 VLC/mpv 不具备通用性，也不能覆盖 Activity 侧的异步解析任务。

### 5. 将“播放无感切换”和“源状态切换”拆成两段责任

播放层面的无感切换由后端 adapter 负责，源状态层面的切换由协调层统一编排，Activity 与播放器仅暴露必要事件。实现上采用以下思路：

- 当前源被应用后，协调层创建新的 `sessionToken`，并异步预解析“紧邻的下一项”。
- 若当前后端 adapter 支持无感续播且自动下一项开启，则协调层将“当前项 + 下一项 + sessionToken”交给 adapter。
- 当后端真正切换到下一媒体项时，adapter 回传 `sessionToken + queueItemId`，协调层校验后更新“逻辑当前源”。
- 更新逻辑当前源后，协调层调用统一的 `StateApplier` 执行轻量同步：
  - 更新标题、`VideoSourceManager`、播放会话元数据。
  - 记录上一项完成状态。
  - 基于下一项自身历史重新装载弹幕、字幕、外挂音轨。
  - 继续预解析再下一项。
- 若 token 已失效、adapter 不支持无感续播或预准备失败，则协调层通过 `FallbackSwitcher` 回退到现有重建路径。
- `applyPlaySource()` 保留为“首个源进入、手动切源、非 Media3、降级回退、异常恢复”等场景的完整重建路径。

这样可以避免为了逻辑源切换而重建整个 Activity/播放器实例，同时也不把源解析职责、状态同步职责和后端能力耦合在一起。

备选方案：

- 让 `Media3VideoPlayer` 直接持有 `BaseVideoSource` 并自己管理顺序：会把业务源模型耦合进内核层。
- 仍然使用 `onCompletion() -> switchVideoSource()`，只是把下一项更早解析出来：虽然能减少等待，但不能消除整段重建。

### 6. 每个视频仍按独立源处理，文件级绑定状态不跨项继承

本次能力解决的是“当前顺序中的下一项能否更顺滑地接上”，而不是把多个文件合并成一个虚拟文件。因此切换到下一项后，系统仍以目标视频自身状态为准：

- 标题、唯一标识、历史进度、媒体会话信息切换为目标视频。
- 若目标视频已有自己的历史字幕、弹幕、外挂音轨绑定，则恢复目标视频自己的绑定。
- 若目标视频没有自己的绑定，则不强行沿用上一项的文件级绑定。
- 播放器全局偏好仍然连续有效，例如倍速、字幕样式、弹幕样式、自动下一项开关等。

这条边界可以避免“上一集外挂字幕泄漏到下一集”之类的副作用，也与现有“手动切到另一文件时按目标文件自身历史恢复”的行为保持一致。

备选方案：

- 默认继承上一项的文件级外挂资源：对独立视频不安全，容易造成误绑定。
- 完全重置所有运行态偏好：会破坏连续观看体验。

### 7. 下一项预准备采用“提前解析 + 失败降级”的策略

为了实现“尽量无感切换”，下一项不能等到当前项结束后才开始解析。首版采用“仅预准备紧邻下一项”的策略：

- 当前源进入稳定播放后，协调层异步解析下一项，并把结果绑定到当前 `sessionToken`。
- 只维护一个已解析的下一项，不递归预抓多项，避免额外资源消耗。
- 若解析、URL 构建或队列准备失败，则不影响当前项播放。
- 当前项结束时若无可用队列，则回退到现有完成后切源流程；若回退也不可用，则保持正常完成态，不播放无关内容。

这样既能获得主要收益，也能控制远程存储、鉴权链接、网络抖动带来的副作用。

备选方案：

- 开始播放即递归预准备整条列表：资源浪费大，也更容易遇到过期链接。
- 只在播放结束后再准备下一项：无法满足低感知停顿目标。

### 8. 现有设置项继续作为总开关

本次能力复用现有“自动播放下一项”设置，不新增 UI 分流，也不改文案。对用户来说，打开这个开关后，在 `Media3` 下将获得更顺滑的顺序续播；在其他内核下仍保留原有自动下一项行为。

这样可以避免新增学习成本，也减少 TV 端设置页与遥控器导航调整。

## Risks / Trade-offs

- [风险] 下一项解析依赖存储层 IO 或网络，请求过慢时仍可能赶不上切换窗口。
  - 缓解：提前预准备紧邻下一项，并在失败时回退到现有完成后切源流程。

- [风险] 没有统一协调层时，不同后端会形成多套编排逻辑，后续难以维护。
  - 缓解：先抽出 `Coordinator + Adapter + StateApplier + FallbackSwitcher` 的统一分层，再让 Media3 作为首个实现。

- [风险] 媒体项已经切到下一项，但标题、历史、弹幕/字幕状态同步滞后，造成短暂状态错位。
  - 缓解：要求所有切换事件都携带 `sessionToken + queueItemId`，只有活动会话才能触发状态同步。

- [风险] 文件级外挂资源若未显式清理，可能错误沿用到下一项。
  - 缓解：将“按目标视频自身状态重新加载”作为单独同步步骤处理，而不是复用上一项内存态。

- [风险] `Media3` 新队列逻辑可能与现有恢复播放、播放附加设置、后台会话同步逻辑产生耦合。
  - 缓解：将“自动顺序续播”限制为长度为 2 的当前项/下一项队列，并保留 `applyPlaySource()` 作为统一降级通道。

- [风险] `Media3` 与 `VLC/mpv` 的行为差异会更明显。
  - 缓解：在设计与测试中明确“无感续播仅保证 Media3”，同时要求后续后端必须实现同一套协调 contract 与共享测试用例。

## Migration Plan

- 本次不涉及数据库结构、持久化模型或外部接口迁移。
- 沿用现有“自动播放下一项”设置作为总开关，无需新增配置迁移。
- 首版仅在 `Media3/ExoPlayer` 路径启用新的无感续播实现。
- 若实现后发现兼容性问题，可直接回退到现有 `switchVideoSource() -> applyPlaySource()` 流程，不影响旧能力可用性。

## Open Questions

- 当前阶段无阻塞性开放问题；若后续实现中发现特定存储类型的播放链接存在明显过期风险，再单独补充针对性策略。
