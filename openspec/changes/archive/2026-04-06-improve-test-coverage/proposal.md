## Why

当前仓库已经具备聚合 JaCoCo 报告与分层测试基础，但覆盖率数据仍明显偏低：现有聚合报告显示全项目行覆盖率约为 7.08%、类覆盖率约为 10.08%、分支覆盖率约为 5.02%。测试主要集中在部分核心工具、协议解析与播放器局部能力上，业务层、页面层、回归路径与 TV 端关键交互仍存在大量空白，导致改动后容易出现“能编译、但行为悄悄退化”的问题。

随着播放器、Bilibili、存储、设置与 TV 焦点相关功能持续迭代，仓库需要一套更明确的“补齐测试逻辑并持续提升覆盖率”的变更方案：不仅补测试，还要定义覆盖率基线、优先级、验证闭环与可执行的验收方式，避免覆盖率提升停留在一次性补丁层面。

## What Changes

- 为仓库新增“测试覆盖率改进”能力定义，明确当前覆盖率基线、优先补齐的模块范围与验收要求。
- 基于现有聚合报告，对低覆盖率或高回归风险模块补充缺失测试，优先覆盖核心业务逻辑、状态编排、解析转换、错误分支与 TV 关键交互路径。
- 统一单元测试、契约测试、回归测试与必要的仪器测试的分工，减少“所有问题都丢给 UI 测试”或“只有 happy path 单测”的失衡情况。
- 将覆盖率提升过程纳入现有 Gradle 验证闭环，确保本地与 CI 能稳定生成覆盖率结果，并据此评估改动是否真正提升质量。
- 对暂不适合高成本 UI 自动化覆盖的场景，要求优先下沉可测试边界，通过 ViewModel、协调器、Mapper、解析器、仓储与适配层测试提高有效覆盖率。

## Capabilities

### New Capabilities
- `test-coverage-improvement`: 定义测试覆盖率基线、优先补齐范围、测试类型分层以及覆盖率验证闭环，指导仓库持续提升测试质量与覆盖率。

### Modified Capabilities
- 无

## Impact

- 受影响范围包括 `build.gradle.kts` 中的聚合覆盖率任务、相关模块的 `src/test` / `src/androidTest` 目录，以及需要补测的业务与基础设施代码。
- 高优先级影响模块预计包括 `app`、`player_component`、`storage_component`、`anime_component`、`user_component` 以及若干覆盖率仍较低但回归成本较高的核心支撑模块。
- 需要梳理“哪些逻辑应通过 JVM 单测覆盖、哪些场景必须通过 Android 仪器测试或 TV/DPAD 冒烟验证覆盖”，并形成一致策略。
- 可能涉及 JaCoCo 报告口径、测试任务编排、回归测试入口与提交前验证要求的调整，但不涉及对外 API 或用户可见功能变更。
