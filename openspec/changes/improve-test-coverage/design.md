## Context

当前仓库已经具备多模块 Android 测试基础设施：各模块存在 `src/test` / `src/androidTest`，根项目也已配置聚合 JaCoCo 任务 `jacocoTestReport`。但从现有聚合报告看，仓库整体覆盖率仍明显偏低（行覆盖率约 7.08%、类覆盖率约 10.08%、分支覆盖率约 5.02%），并且测试覆盖高度不均：部分基础能力、协议解析、日志与播放器内核已有较多测试，而 `app`、`anime_component`、`storage_component`、`user_component` 等用户路径更重、TV 交互更敏感的模块仍有大量空白。

该仓库以 TV/遥控器 DPAD 交互为先，很多高风险回归点并不只体现在纯业务逻辑上，还涉及页面焦点、设置项行为、播放入口、返回栈与 Android 集成行为。因此本次变更不能简单理解为“多写几个单测”，而需要把覆盖率提升拆成可持续的工程能力：建立基线、识别优先级、选择合适测试层级、运行统一验证闭环，并尽量复用现有 Gradle/JaCoCo 能力，而不是引入一套新的测试治理体系。

## Goals / Non-Goals

**Goals:**
- 基于现有聚合报告建立仓库当前覆盖率基线，并据此识别优先补测的模块与 package 热点。
- 为不同类型的代码建立分层测试策略：纯逻辑优先使用 JVM 单测/契约测试，Android/TV 运行时行为使用仪器测试或冒烟测试覆盖。
- 将“补测试”和“验证覆盖率提升”纳入统一的 Gradle 闭环，保证本地和 CI 都能重复执行并得到一致结论。
- 优先补齐高回归风险区域的测试，包括状态协调器、Mapper、解析器、仓储、设置行为、播放入口与 TV/DPAD 关键路径。
- 采用分阶段、基线感知的方式提升覆盖率，避免一刀切的全仓库硬阈值导致实施成本失控。

**Non-Goals:**
- 本次不追求一次性把全仓库覆盖率提升到高阈值，也不要求所有模块立刻达成统一百分比目标。
- 本次不要求为每个页面都编写完整 UI 自动化用例，尤其不把所有缺口都转嫁为高维护成本的仪器测试。
- 本次不切换到新的覆盖率引擎或替换现有 Gradle/JaCoCo 体系，除非后续实施中证明确有必要。
- 本次不为了追求覆盖率数字而大规模改写生产代码结构；只有在提升可测试性同时能改善职责边界时才做结构优化。

## Decisions

### 1. 以现有聚合 JaCoCo 报告作为统一基线来源

仓库已经具备 `jacocoTestReport` 聚合任务，并能输出全项目 XML/HTML 报告，因此本次设计不新增并行的覆盖率数据源，而是以现有聚合报告作为统一基线。所有“当前覆盖率是多少”“哪些区域最值得补测”的判断，都优先基于该报告得出。

选择该方案的原因是：
- 避免出现多个报表口径不一致的问题；
- 复用现有 Gradle 配置与 CI 习惯，降低接入成本；
- 便于后续实现按 module/package 继续做增量汇总，而不是推倒重来。

备选方案：
- 引入新的覆盖率插件或外部统计平台作为主数据源：实现成本更高，且会与现有任务口径冲突。
- 只看单模块测试数量，不看实际覆盖报告：容易出现“测试文件很多但关键逻辑没覆盖”的误判。

### 2. 采用“风险优先 + 热点优先”的补测顺序，而不是平均撒网

覆盖率提升不应按模块平均分配工作量，而应优先处理“当前覆盖率低、用户影响大、回归代价高”的区域。首批目标优先锁定 `app`、`player_component`、`storage_component`、`anime_component`、`user_component` 以及覆盖率报告中暴露出的低覆盖 package 热点；核心支撑模块则按风险与收益插队处理。

选择该方案的原因是：
- 用户路径与 TV 交互回归的业务损失更大；
- 先解决高风险缺口，能更快提升真实质量，而非只美化平均值；
- 与现有报告中“个别包覆盖很高、整体仍偏低”的现状相匹配。

备选方案：
- 要求每个模块都先补同样数量的测试：容易稀释投入，难以优先消除高风险回归点。
- 只围绕当前改动文件补测试：短期有效，但无法系统性改善长期空白。

### 3. 建立“逻辑优先单测，平台相关再上仪器测试”的分层策略

对 ViewModel、协调器、Mapper、解析器、仓储、策略类、错误映射与状态转换等逻辑边界，优先补 JVM 单元测试或契约测试；仅当行为依赖 Android Framework、播放内核、Activity/Fragment 生命周期、DPAD 焦点导航或系统服务时，才要求仪器测试或 TV 冒烟验证。

选择该方案的原因是：
- JVM 测试稳定、执行快、定位问题直接，更适合作为覆盖率提升的主力；
- 仪器测试更适合兜底运行时真实行为，而不是承载所有分支验证；
- 符合仓库当前已有的测试分布与 TV 产品特性。

备选方案：
- 大量依赖仪器/UI 自动化提升覆盖率：维护成本高、易脆弱、反馈慢。
- 只写 JVM 测试，不做运行时回归：无法覆盖 TV 焦点、生命周期与 Android 集成问题。

### 4. 覆盖率门禁采用“基线感知的渐进式目标”，不直接启用高全局阈值

考虑到当前基线较低，直接设置激进的全仓库覆盖率阈值会让变更落地几乎不可执行。本次设计采用渐进式策略：先记录基线与首批目标范围，再针对目标模块/包或本次提升波次定义增量要求，后续再逐步收紧门禁。

选择该方案的原因是：
- 能在当前低基线下真实推动改进，而不是制造大面积阻塞；
- 允许先完成“能力建立 + 重点补测”，再过渡到更严格的自动化约束；
- 更符合多模块存量仓库的治理节奏。

备选方案：
- 立即要求全仓库达到统一硬阈值：可执行性差，容易逼出低价值测试。
- 完全不设门禁，只靠人工关注：覆盖率提升难以持续，容易回落。

### 5. 以“测试证据 + 覆盖率结果 + BUILD 状态”构成验证闭环

每一波覆盖率改进都必须包含可复现的验证步骤：至少运行与改动相关的 Gradle 测试任务，并生成聚合或范围内覆盖率结果；汇报时必须明确说明输出尾部是 `BUILD SUCCESSFUL` 还是 `BUILD FAILED`。覆盖率数据、测试结果与构建状态共同构成验收证据，而不是只给出“我加了几个测试文件”。

选择该方案的原因是：
- 将“测试写了”与“测试真的跑通了”区分开来；
- 保持与仓库现有构建验证规则一致；
- 便于后续在 PR/CI 中形成统一格式的测试证据。

备选方案：
- 只检查测试文件是否存在：不能说明行为已被验证。
- 只看 BUILD 成功，不看覆盖率变化：无法判断质量是否真正提升。

### 6. TV/DPAD 关键路径只保留必要的冒烟覆盖，不追求全量界面自动化

由于仓库以 TV 体验为先，凡是影响焦点、导航、设置操作、播放入口/退出的改动，都必须保留 DPAD 可达性的验证；但验证方式以少量高价值冒烟用例或可复现仪器路径为主，而不是为每个界面状态都构建重型 UI 自动化。

选择该方案的原因是：
- TV 端最怕“焦点丢失、不可达、不可返回”类退化；
- 少量稳定的主路径测试更容易长期维护；
- 与 AGENTS 中的 TV 回归要求一致。

备选方案：
- 不对 TV 路径做自动化或冒烟验证：高风险改动容易漏检。
- 为每个页面写全套 UI 自动化：成本高且脆弱。

## Risks / Trade-offs

- [风险] 覆盖率提升可能被误导为“追数字”，产生大量低价值测试。  
  缓解：要求优先覆盖高回归风险逻辑与真实用户路径，并用需求/场景驱动测试而不是机械刷行数。

- [风险] 仪器测试数量增加后，整体验证耗时和波动性会上升。  
  缓解：坚持“逻辑优先单测、运行时关键路径少量冒烟”的分层策略，避免把分支验证都堆到设备测试中。

- [风险] 若没有明确的优先级，补测工作会分散在低收益区域，整体提升有限。  
  缓解：基于现有聚合报告与业务风险确定首批目标模块/包，按波次推进。

- [风险] 只看全仓库总覆盖率，可能掩盖关键 package 长期为空白的事实。  
  缓解：在总量之外同步关注模块/package 热点，优先追踪低覆盖且高风险区域。

- [风险] 渐进式门禁如果定义过松，后续容易停在“永远过渡中”。  
  缓解：在实施任务中明确每一波需要交付的测试范围、验证命令和目标结果，为后续收紧门禁留出基线。

## Migration Plan

- 第一阶段：基于现有 `jacocoTestReport` 确认全仓库与 package 热点基线，梳理首批补测范围。
- 第二阶段：按模块波次补充 JVM 单测、契约测试与必要的仪器/冒烟测试，并同步修正可测试性边界。
- 第三阶段：将覆盖率结果纳入稳定验证流程，必要时为目标模块或波次引入增量门禁。
- 若实施过程中发现门禁策略过于激进，可先回退自动阻断规则，仅保留测试与报表生成能力；新增测试本身应保留，不需要回滚。
